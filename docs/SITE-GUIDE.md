# NAOJUN STUDIOS サイト設計・ページ作成規約

Version 1.0 / 2026-10-04。今後の追加・改修では、最初にこの文書を読む。
実装上の正は共通CSS・テンプレート・台帳。変更時は文書も同じPRで更新する。

## 1. 共通テーマと語り口

正式なマスターブランド名は **NAOJUN STUDIOS**。サイトのロゴ、title、OGP、構造化データ、
copyright、About本文など、訪問者に見えるスタジオ名はこの表記へ統一する。
`naojun.jp` はブランド名変更後も正規ドメインとして維持する。作品固有名として既に定着している
`NaoJun Investment Observatory` と `NaoJun Stay Atlas`、内部のスクリプト名・User-Agentなどは
マスターブランド表記とは別物なので、名称変更の必要がない限り維持する。

**日々に、小さな発明を。 / Small studio. Useful creations.**

暮らしから生まれる便利さ、遊び、観察を、ふたりの視点で形にする小さな制作スタジオ。
「Useful / Considered / Ongoing（役立つ・よく考える・育て続ける）」を判断軸にする。
作品の種類が増えても、この約束に結びつく用途を先に説明する。

- 日本語が主言語。英語は短いラベルや作品固有名、編集上のアクセントに限定する。
- 短く具体的に書く。誰が、何を、どう使えるかが分かる文を優先する。
- 実装済みの機能、予定、制限を区別する。誇張した性能・利用者数・受賞歴を加えない。
- AIは制作手段。記事の調査・編集者表示は残し、読者への価値より内部技術を前に出さない。
- 作品固有の世界観は認める。グローバルのロゴ・導線・本文の読みやすさは共有する。

## 2. ページの役割

| ページ | 訪問者にしてほしいこと | 構成と雰囲気 |
|---|---|---|
| トップ | スタジオを理解し、作品・記事・映像へ進む | 動くシンボル、選抜作品、便利な道具、YouTube、Journal、紹介。余白を広く取り、掲載点数を増やしすぎない |
| Works | 作品を比較して選ぶ | 全公開作品の台帳。統一カード、種類・公開状態・短い説明、絞り込み。h1の次は各作品h2 |
| 作品詳細 | 利用できること・条件を理解し、試す／購入する | 作品名、ひとことで用途、主要CTA、実画面・デモ、機能、動作環境、価格・データの扱い、問い合わせ・一覧へ戻る |
| Journal一覧 | 分野と発行時点から読む記事を選ぶ | 内容・日付を優先。投資／教育の区別を保ち、最新記事は各feed.jsonに従う |
| 記事 | 内容を理解し、出典を確かめる | パンくず、種類・日付、見出し、要約、調査者・対象期間、結論、根拠と分析、留保、出典。本文に装飾的な動きを置かない |
| About | 誰がどの考えで作るか理解する | ふたりの視点、制作の原則、問い合わせ。架空の経歴・チーム規模は書かない |
| Contact・規約 | 迷わず手続き／条件確認を終える | 共通の外枠に、落ち着いた見出しとフォーム・本文。機能性を最優先 |

記事はWorksに1本ずつ登録しない。研究・編集の仕組みを作品として掲載し、個々の記事は
分野別feedで管理する。YouTubeチャンネルへのリンクと個別の映像作品も区別する。
実際の映像作品を追加する場合だけ `film` の作品レコードを作る。

## 3. 見た目の基準

| 要素 | 基準 | 実装 |
|---|---|---|
| 背景 | やや温かい紙色 `#f4f3ec` | `--paper` |
| 本文 | 墨に近い `#20251f` | `--ink` |
| 主アクセント | cobalt `#2445db`。リンク・要点に限定 | `--cobalt` |
| 補助アクセント | acid `#e3f291`。暗い背景の強調など | `--acid` |
| 補助文字／罫線 | `#555d50` / `#d4d7cb` | `--quiet` / `--rule` |
| 基本文字 | OS標準のsans。日本語は読みやすさ優先 | `.studio-site` |
| 編集的な見出し | Georgia系serifはAbout・Journalの短い英文に使用 | 本文全体には適用しない |
| 本文幅 | 記事は最大780px、17px／スマホ16px、行高2 | `.studio-article` |
| レイアウト | 主要領域は最大1440px。スマホ左右20px | `.container` |
| 形 | 細い罫線、基本は角を立てる。カードや影を乱用しない | `studio.css` |
| 余白 | 原則8px単位。本文内とセクション間で強弱を作る | 既存コンポーネントの値を踏襲 |

色・共通サイズの変更は `assets/css/studio.css` に集約する。記事用・商品用CSSを
読んだ後にstudio.cssを読む。ページ内styleで共通規約を上書きしない。
記事の長い日本語タイトルを、トップの大きな英文見出しのサイズで表示しない。
表は表自身または専用領域だけを横スクロールさせ、ページ全体を横にはみ出させない。
スクロールする表はキーボードでも到達・操作できるようにする。同期処理が表のフォーカスと名称を補う。

## 4. 共通UI・リンク

- ヘッダーはWorks / Journal / About / Contact / Store。並びをページごとに変えない。
- フッターはWorks / About / Contact / Privacy / YouTube / RSS。YouTubeの正は
  `content/site.json` のチャンネルID。推測したハンドル・別アカウントへ差し替えない。
- 外部アカウントの表示名は可能な範囲で `NAOJUN STUDIOS` に揃える。URLやhandleは変更成功を
  確認してからサイト側を切り替え、先に既存の有効URLを壊さない。STORESの購入URLは特に
  商品購入導線なので、ストア側変更前にサイトだけを新URLへ推測変更しない。
- 新しいタブで開くリンクには、その旨を支援技術へ伝え、`rel="noopener noreferrer"` を付ける。
- 作品・記事への内部リンクはルート相対の正規URLを使う。既存URLは移動しない。
- 各ページに1つのh1、本文スキップ、main、共通ナビを置く。記事には分野一覧へのパンくずを置く。
- 同ページを表すメニューだけ `aria-current="page"`。記事から分野一覧へのリンクは現在ページ扱いしない。
- メニューはキーボードとタッチで操作可能にする。Escapeで閉じ、起点へフォーカスを戻す。
- 固定高さで日本語を切り落とさない。視覚的な省略は全文に到達できる場合だけ。

## 5. 作品台帳と画像

`content/works.json` がトップの選抜カードとWorks一覧の共通情報源。

| 項目 | 意味 |
|---|---|
| `id` | 永続ID。小文字英数字とハイフン、重複不可 |
| `title` / `summary` | 正式表示名／用途を説明する短い文章 |
| `href` | 存在するサイト内URLか、確認済み外部HTTPS URL |
| `category` | companion / game / tool / research / film |
| `label` | DESKTOP COMPANIONなど短い補助分類 |
| `status` | 無料・販売中・Previewなど、実際の利用条件に合う表示 |
| `cover` | `_partials/covers/` 内の作品固有HTML。画像またはCSS/SVG構成 |
| `featured` | trueの場合にトップの選抜作品へ掲載。通常2件、最大4件を編集目安とする |

カード番号・件数・絞り込み項目は自動生成。生成済みカードだけを直接直さない。
トップの短い告知は `content/site.json` の `spotlight_id` で作品台帳を参照し、名称・公開状態・リンクを揃える。
カバー内の状態バッジは `{{STATUS}}` を使い、状態の文言を二重管理しない。
作品詳細の機能・価格・バージョンを変更したら、台帳・トップの告知・購入先も照合する。
Previewを販売中と書かない。販売価格を複数箇所へ安易に複製しない。

カバーは作品ごとの世界観を持たせる。製品には本物の画面、ゲーム・映像には権利を持つ
キービジュアルを使う。描画だけで実画面を装わない。画像にはaltとwidth/heightを指定し、
装飾図形は支援技術から隠す。ファーストビュー以外は遅延読み込みを基本とする。
YouTubeはまず通常リンク。埋め込みを加える場合は明示操作で読み込み、無音を含めて
自動再生を既定にしない。視聴前から不要な外部通信を増やさない。

## 6. 記事規約

- `investment/feed.json` と `admissions/feed.json` が記事名・公開日・要約・パスの正。
  見出し・一覧・SEO情報を一致させる。発行後の更新は公開日と更新日を区別する。
- 結論を先に示し、事実、解釈、予測、留保を分ける。重要な主張の近くに出典を置く。
- 引用は引用と分かる表示にする。グラフ・表には対象期間、単位、情報源を付ける。
- リンクは色だけに頼らず下線を付ける。注記を小さすぎる文字や薄すぎる色にしない。
- 本文の主張・データはデザイン改修に混ぜて変更しない。内容修正は別途根拠を確認する。
- 分野別 `PUBLISHER.md` の編集・公開契約を併用する。共通規約は既存の公開権限を変更しない。

## 7. 追加・更新手順

1. この規約と必要なPUBLISHER契約を読む。最新mainから独立した作業ブランチを作る。
2. 作品は `works/_templates/project-template.html`、記事は各分野の `_templates/` を出発点にする。
   `{{...}}` をすべて置換する。作品固有レイアウトは共通外枠の内側で設計する。
3. 作品台帳または記事feedを更新する。トップ掲載は編集判断で選び、全件を押し込まない。
4. `python scripts/sync_studio.py` を実行。共通ヘッダー・フッター・カード・記事外枠を反映する。
5. `python scripts/build_discovery.py` を実行。canonical・OGP・構造化データ・sitemap・RSSを再生成する。
6. 次の検査と変更箇所の既存smokeを実行。HTMLと台帳・テンプレートを同じPRに含める。

```text
python scripts/test_studio_contract.py
python scripts/sync_studio.py --check
python scripts/design-integrity.py
python scripts/build_discovery.py --check
```

7. 360/390/768/1440pxで確認。新しい見た目・操作はChromiumとWebKitで検証し、
   スマホ／PCの画像を実際に確認する。ブラウザ検証方法は `docs/design-20261004.md` を参照。
8. CI成功と差分確認の後、既存の公開契約に沿って公開。live URL、画像・CSS読込、主要CTAを確認する。

`Studio Design Contract` CIは共通部品・台帳・テンプレートの反映漏れを失敗として検出する。
チェックを回避するために生成物だけを修正したり、判定を弱めたりしない。

## 8. 品質の完了条件

- 内容：作品の利用条件や記事名・日付が入口と詳細で矛盾しない。
- 視覚：明確な主役、見出し階層、余白のリズム。文字・画像の潰れ、欠け、意図しない折返しがない。
- 操作：主要CTA、戻る導線、キーボード、モバイルメニュー、JavaScript無効時の基本導線が機能する。
- 配慮：本文の十分なコントラスト、暗い背景でも見えるフォーカス、reduced-motion、操作による停止。
- 速度：不要なライブラリ・フォント・自動再生を増やさない。画面外の描画を止め、画像寸法でずれを抑える。
- 整合：新しいページも共通UIを使い、SEOと既存解析・記事更新・販売導線を維持する。

受賞は外部審査であり、自動検査の合格を受賞水準の証明としない。

## 9. 適用範囲と例外

スタジオの紹介・作品紹介・記事にはこの規約を適用する。`tools/3lines/` と `stay/` のような
独立したアプリ画面は、操作密度や固有のUIを維持してよい。今回それらのアプリ内部UIは
変更しない。新規作品はまず共通の紹介ページを作り、必要ならアプリへ遷移する。
既存の `works/sample-product/` は旧サンプル。新規作成の元にせず、新しい非公開テンプレートを使う。

別デザインが必要なら、理由・適用範囲・共通の戻り先・検証結果をPRに記録する。
ロゴ・所有者表示・解析設定を別サイトと混用しない。規約の変更は意図した全ページの
比較画像とともに行い、個別ページだけの偶発的な逸脱にしない。
