AI開発・セキュリティ日報｜2026年10月27日号

Chrome 156のCritical 4件、Tailscale SSH・Serveの修正、LiteLLM悪性配布版とBrotli/AWS Lambdaの条件別対処。対象日と事後追補を区別。

調査・編集：K.A.N.A.D.E.　／　確認時点：2026-10-30 事後復旧版 JST

対象日：2026年10月27日。実際の初回公開日：2026年10月30日。 10月28〜30日に判明した事項は事後追補として区別し、当時の既知情報と混同しません。

本日の結論

Googleは2026年10月27日、Chrome 156に計52件のセキュリティ修正を公表し、4件をCriticalと評価。 Windows/Mac 156.0.8078.73/.74、Linux 156.0.8078.73の展開を案内した。公開日に確認できたChrome更新を最優先の確認事項とし、端末の実版を確認して正規更新する。Criticalは深刻度であり実悪用を意味しない。10月27日公式告知（新しいタブ）。

追加の重要確認： 10月27日（米東部時間）のCISA発表では、Brotli（CVE-2026-111497）とAdobe Commerce/Magento（CVE-2026-48356）が悪用確認済みのKEVに追加された。発表はJSTでは10月28日04:30であり、これは10月27日号に対する事後追補であって、10月27日JSTに把握済みだったと主張しない。Brotliの境界外書き込み自体はJPCERT/CCが10月26日に注意喚起しており、Node.js・Bun・Python向け実装などの組み込み影響を確認すべき案件である。CISA公式発表（新しいタブ）、JPCERT/CC公式注意喚起（新しいタブ）。

Mozillaは10月27日、Firefox 159、ESR 153.6/115.44、Thunderbird 159/153.6について5件の製品別セキュリティ勧告（MFSA 2026-118〜122）を公開した。Firefox 159にはHigh評価のsandbox escapeやuse-after-freeなどが含まれる。利用製品の正規更新を確認する。重大度と実際の悪用は区別する。Mozilla公式一覧（新しいタブ）、Firefox 159勧告（新しいタブ）。

AI開発のサプライチェーン上の重要既報： Microsoftが10月23日に公表した分析によると、10月21日に配布されたLiteLLM 1.107.0には資格情報を収集する悪意あるコードが含まれた。Python起動時に処理が走り得るため、LiteLLMを明示的にimportしなくても影響する可能性がある。一方、1.82.7と1.82.8も2026年3月24日の別のPyPI侵害で配布された悪性版であり、GitHub Advisory（新しいタブ）は3版すべてを対象に挙げる。3月の公式Proxy Docker imageはLiteLLM公式報告（新しいタブ）で影響対象外とされるため、3月・10月の配布経路を混同しない。

3版のいずれかを使った疑いのある端末・CI/依存関係について、該当する配布時期・経路を調べ、当該Python環境で不用意にpython/pipを起動せず、清浄な環境から影響を調査し、隔離・再構築・アクセスできた資格情報やセッションの失効/ローテーションを検討する。単にパッケージを消すだけでは残存リスクがある。10/27当日発覚の事件ではなく、既報の優先確認事項であり、非利用者が侵害されたと断定しない。Microsoftによる10/23の分析（新しいタブ）。

開発・インフラ上の条件付きP1： AWSは10月26日（JSTでは10月27日）に、@aws-cdk/aws-redshift-alphaのCVE-2026-115418を公表した。実験モジュールでconstruct値を変更可能な場合に、Redshift superuser権限のSQLが意図しない形に変更され得る。対象moduleの利用有無と版数を確認し、修正版へ更新後にPUBLIC grantを確認する。全AWS利用者やRedshift本体に無条件に当てはまる脆弱性ではない。 AWS公式速報（新しいタブ）。

10月26日付でTailscaleが公開したセキュリティ通知4件は、SSHやServeを使う個人開発環境に関係する。通常のVPN接続だけを使う全員が同じ条件で影響を受けるわけではない。SSH転送とServeのbackend設定を確認し、該当するノードはv1.104.4以上へ更新することが現時点の公式対処となる。v1.104.4の公開は10月28日であり、10月27日時点で修正版が利用可能だったかのようには記載しない。出典：Tailscale Security Bulletins（新しいタブ）、Changelog（新しいタブ）。

AIによる脆弱性発見：Anthropicが5系統の攻撃チェーンを公表

Anthropic Frontier Red Teamは10月27日、研究モデルでChrome、Safari、Android、Windows、Linuxの5系統の攻撃チェーンを実証し、関係ベンダーへ協調開示したと発表した。WindowsのHTTP/3実装に関係するCVE-2026-33096（遠隔DoS）、Linux multipath TCPに関係するCVE-2026-98432（遠隔コード実行）なども紹介している。これは研究での実証と修正報告であり、攻撃者による実悪用や各端末へのパッチ適用を証明するものではない。Anthropic公式研究（新しいタブ）。

AnthropicはChromeに関して、研究由来の62 CVEがChrome 156までに修正されたと説明する。この数と、Googleの10月27日付Chrome更新での52件の修正は集計範囲が異なる可能性がある。両者を同一件数として置き換えたり、重複のない114件として足したりしない。OS/ブラウザの修正版適用については提供元の案内に従って確認する。

10月27日付のAI開発運用トピック

GitHubは組織GitHub AppからCopilot SDKをserver-to-server認証で呼べるpublic previewを公表した。導入時は組織側のCopilot Requests権限が必要で、使用量は組織に課金される。既存アカウントで自動的に有効化された無料機能ではない。GitHub公式（新しいタブ）。

AWSはElastic BeanstalkのAmazon Linux 2023環境向けに、10月26日までのセキュリティ修正を含むplatform updatesを発表し、Node.js 26とPython 3.15の新しいplatform branchを追加した。配布地域と実際の適用版は環境ごとに確認する。AWS公式（新しいタブ）。

OpenAIはOracleアプリとChatGPTの連携計画、Oracle AI Workspace構想を発表した。一般利用者へのすべての新機能の提供開始を意味するわけではない。OpenAI公式（新しいタブ）。

優先度P1：Chrome 156のCritical 4件

Google分類Criticalの4件は CVE-2026-118306（FileSystemメモリ破損）、CVE-2026-118331（FileAPI入力検証不備）、CVE-2026-118348（Skia入力検証不備）、CVE-2026-118344（Layout use-after-free）。メモリ破損などの説明はGoogleの公開分類に基づき、これだけで特定端末の侵害・遠隔コード実行・実悪用を断定しない。公式出典（新しいタブ）。Chromeを使う端末では正規更新の適用後にバージョンを独立確認する。更新は段階的に配布される。

優先度P1：Brotliの組み込み製品とCISA KEV対象の管理

Brotli（CVE-2026-111497）は圧縮データを展開する製品や依存ライブラリの確認が必要。JPCERT/CCは2026年10月26日に注意喚起し、Node.js・Bun・Python向けパッケージ等に波及し得ると説明した。Node.js 24系列の24.22.1は10月21日の公式セキュリティリリースに修正を含むが、別系列・別製品の修正版は各提供元で独立確認する。JPCERT/CC（新しいタブ）、Node.js 24.22.1（新しいタブ）。CISAの10/27米東部時間発表は10/28 JSTの事後情報として掲載し、当時の対処可能性を偽らない。Adobe Commerce/Magentoを使う環境は同日のKEV追加（CVE-2026-48356）を確認する。使っていない製品の影響を断定しない。

優先度P1：Tailscaleを該当構成で使う開発・運用環境

  • TS-2026-014：SSH Unixソケット転送。Tailscale SSHで認証済みピアにローカル／リモート転送を許す構成では、特権ソケットへのアクセスを許す可能性があった。修正後は認証されたユーザーの権限で転送する。SSHを使うだけで無条件にroot権限が得られるという意味ではない。
  • TS-2026-015：SSHセッションのメモリ枯渇。Tailscale SSHの認証済みセッションで特定のメッセージを連続送信すると、tailscaledのメモリ消費が増え、ノードの通信に影響する停止につながり得た。DoSの問題であり、単独で遠隔コード実行を示すものではない。
  • TS-2026-016：ServeのUnixソケットbackend。Unixソケット転送とbackendの指定条件が重なると、tailscaledなどの特権ソケットにアクセスする危険があった。Serveのすべての配置ではなく、Unix backendや設定変更権限に着目する。
  • TS-2026-017：Serve TLSと複数mount。HTTP/2の同一接続に異なる権限条件のmountがあると、capabilityヘッダーが別リクエストに混ざる可能性があった。権限情報を利用して許可判定するアプリで影響が生じ得る。

影響条件の詳細はTailscaleの4件の公式セキュリティ通知（新しいタブ）に記載されている。実際に悪用された台数や侵害の発生について、この資料だけから断定しない。

AI推論基盤のP1：旧AWS Multi Model Serverは修正版なし

AWSは10月23日（JST10月24日）、サポート終了済みのMulti Model Server（MMS、公開版1.1.11以下すべて）について、モデルarchiveの展開によるファイル書込み先逸脱（CVE-2026-115812）と、モデル取得時の意図しないネットワーク宛先へのアクセス（CVE-2026-115813）を公表した。管理APIが認証なしで信頼されないネットワークから届く構成が特に危険。修正版はなく、AWSはサポート中のモデル提供基盤への移行を推奨する。暫定的に管理APIの到達元を絞るが、SageMaker型の同一ポート構成では単純なloopback化ができない。採用していない環境への一律の脆弱性断定は避ける。AWS公式2026-148-AWS（新しいタブ）。

同じ10月23日発表のAWS MCP Server run_script sandbox検証不備（CVE-2026-115845）はmanaged service側で修正済み、顧客操作不要。認証済み利用者の隔離セッション内という条件を旧MMSの無認証管理API問題と混同しない。AWS公式2026-149-AWS（新しいタブ）。

Brotliの事後更新：AWS Lambdaではバージョン名だけで修復を判断しない

AWSの10月28日15:00 PDT（JST29日07:00）公表・10月29日14:00 PDT（JST30日06:00）更新の通知によると、Lambda Node.js 24 runtimeはNode.js 24.22.1の既知の回帰を避けるため、AWSが現行安定版に対象のBrotli修正を当てて段階配信する。アプリ側でnode --versionを確認するだけでは、このランタイムパッチの適用を判定できない。AWSはcold-startのINIT_START行でpatch versionを確認するよう案内している。これは10月27日号への事後追補であり、当日の修正済み事実として書かない。AWS公式2026-155-AWS（新しいタブ）。

サポート終了版は移行が前提： Lambda Node.js 18/20はこのセキュリティ更新を受け取らない。Phase 2で自動修正されると待たず、サポートされているNode.js 22/24/26へ移行し、移行後の適用状態を確認する。修正を取り込む操作： LambdaのZIP形式のNode.js 22/24/26関数では、対象リージョンのPhase 1適用後、コードまたは設定を実際に変更して更新する（UpdateFunctionCode／UpdateFunctionConfiguration）。変更内容が同じままの更新ではランタイムpatchを取得できない。Auto runtime updateの関数はPhase 2で段階的に更新されるが、予定日だけで反映済みと判断しない。Lambdaコンテナ形式では更新済みのbase imageを使って再ビルド・再デプロイする。更新後は新しいcold startのCloudWatch INIT_START行の識別子を確認し、Node.js 22はnodejs:22.mainline.v157以上、Node.js 24はnodejs:24.mainline.v114以上を修正到達の目安とする。Node.js 24のprocess.versionにはAWS独自patchが反映されない。自前で同梱したBrotliライブラリは別途確認・更新が必要。AWS一次資料・適用と検証手順（新しいタブ）（10月30日JST確認した事後追補）。

具体的な確認・修復・検収

まずノードごとのTailscaleバージョンを tailscale version で確認し、Tailscale SSHを有効にしているか、forwardingを許すか、ServeでUnixソケットやTLS複数mountを使っているかを整理する。該当環境には、10月28日公開のv1.104.4以上を適用する。公式変更履歴（新しいタブ）で最新の修正情報を確認したうえで、更新後はノードへの通常接続、SSH、Serveの公開機能、ログとサービス到達性を確認する。

SSH forwardingを業務に使っていない構成では、公式通知にある TS_SSH_DISABLE_FORWARDING=1 をservice環境で設定し再起動する緩和策もある。ただし変更は既存設定と復旧経路の確認後に行う。実行環境で前方互換性を推測して自動適用しない。障害があれば事前保存したservice設定へ戻す。
